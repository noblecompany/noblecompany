# 노블컴퍼니 홈페이지 — 기능 및 어드민 설계

작성일 2026-08-03 · **범위 확정 2026-08-05** · 대상 저장소 `site_noble`

현재 사이트는 **정적 SPA**(React + Vite, GitHub Pages 배포)입니다.
모든 콘텐츠가 `src/data/*.ts` 에 하드코딩돼 있고, 문의·지원은 `mailto:` 로 처리합니다.
이 문서는 "실제로 동작해야 하는 기능"과 그것을 운영할 **어드민**을 설계합니다.

---

## 0. 확정 범위 (2026-08-05)

| 구분 | 결정 |
|---|---|
| **진행** | 접수·인증·개인정보(A1~A4) + 콘텐츠 등록 B1~B6 + 팝업·통계 C1·C2 |
| **추가 필수** | 접수 알림(F6), 스팸·봇 방지(F8), 정책 페이지(F12), 감사 로그(F15) — 선택 범위의 전제조건 |
| **제외** | 사이트 문구 편집(F10) — 히어로 카피·재무 지표 등은 **하드코딩 유지** |
| **보류** | 포트폴리오 성과(Result) 데이터 확보 — 하드코딩으로 진행해도 무방 판단 |
| **C1·C2** | 어드민 설정에서 기능별 **on/off 토글** 제공 |
| **어드민 디자인** | 본 사이트 톤(노블 블루·Pretendard·라이트/다크) 유지 + 전문 SaaS 구조 (6.0) |

## 1. 현재 상태 진단

| 영역 | 현재 | 문제 |
|---|---|---|
| 프로젝트 문의 | `Contact.tsx` → `mailto:` | 발송 여부를 서버가 모름. 메일 앱 없는 사용자는 이탈. 접수 이력·통계 없음 |
| 채용 지원 | `CareerDetail.tsx` → `mailto:` | 이력서 첨부를 지원자가 직접 해야 함. 지원자 관리 불가 |
| 채용공고 | `data/careers.ts` | 공고 하나 올리려면 개발자가 코드 수정 → 커밋 → 배포 |
| 포트폴리오 | `data/works.ts` (엑셀에서 자동 생성) | 신규 캠페인 추가 시 동일 문제. 이미지도 `public/portfolio/` 직접 업로드 |
| 회사 정보·복리후생 등 | 각 페이지에 인라인 | 문구 한 줄 수정도 배포 필요 |
| 접근 통계 | 없음 | 어떤 공고·포트폴리오가 조회되는지 모름 |

핵심 결론: **콘텐츠 운영(CRUD)** 과 **접수 처리(폼)** 두 축에 백엔드가 필요합니다.

## 3. 아키텍처 선택

### 3.1 옵션 비교

| 방식 | 장점 | 단점 | 비용(월) |
|---|---|---|---|
| **A. Supabase + Vercel** (권장) | DB·인증·파일스토리지·API가 한 세트. 프론트 그대로 재사용. 어드민도 같은 React 코드베이스 | Supabase 학습 필요 | 0~25달러 |
| B. Headless CMS (Strapi/Sanity) | 어드민 UI를 만들 필요 없음 | 폼 접수·파일 업로드는 별도 구현. 스키마 커스터마이징 제약 | 0~99달러 |
| C. 자체 서버 (Node + PostgreSQL) | 완전한 통제 | 서버 운영·보안·백업 부담. 인력 필요 | 서버비 + 운영공수 |
| D. 폼 서비스만 (Formspree 등) + 공고는 코드 유지 | 가장 빠름 (하루) | F3·F5 미해결. 임시방편 | 0~10달러 |

### 3.2 권장안: **A (Supabase + Vercel)**

```
[방문자] ──> Vercel (정적 프론트 + /api 서버리스 함수)
                 │
                 ├─> Supabase Postgres   (공고·문의·지원·포트폴리오)
                 ├─> Supabase Storage    (이력서 PDF, 캠페인 이미지)
                 ├─> Supabase Auth       (어드민 로그인)
                 └─> HIWORKS SMTP        (접수 알림 메일 — 사내 메일과 동일 채널)
```

> 도메인·DNS는 **가비아**에서 관리 확인 완료(2026-08-05). 메일도 HIWORKS(가비아 계열)라
> 발신 도메인 인증(SPF/DKIM)이 이미 잡혀 있을 가능성이 높아 별도 메일 서비스가 불필요합니다.
> 발송용 계정 1개(예: noreply@e-noble.kr)의 SMTP 정보만 있으면 됩니다.

**배포 이전이 전제입니다.** GitHub Pages는 정적 전용이라 서버 API를 둘 수 없습니다.
Vercel로 옮기면 현재 빌드 설정(`vite.config.ts` 의 `BASE_PATH`)을 루트(`/`)로 되돌리고,
`e-noble.kr` 도메인을 Vercel에 연결하면 됩니다. GitHub Pages는 프리뷰용으로 유지 가능합니다.

> 파일 업로드(F2 이력서)는 브라우저 → Supabase Storage 직접 업로드(signed URL)로 처리해
> 서버리스 함수의 요청 크기 제한(4.5MB)을 우회합니다.

**플랜 정책 (2026-08-05 확정): Supabase 무료 + 매일 자동 ping**

- 무료 플랜은 7일간 요청이 없으면 일시정지되므로, Vercel Cron이 매일 새벽
  `GET /api/jobs` 를 1회 호출해 활동을 유지한다 (비용 $0)
- 운영 중에는 방문자의 공고 조회만으로도 활동이 집계되어 실질 리스크는 낮음
- 오픈 후 한 달 트래픽을 보고 Pro($25/월, 일시정지 없음·백업 7일) 전환 여부 재검토.
  코드는 동일하므로 플랜 변경만으로 전환 가능

```sql
-- 4.1 채용공고 (현재 src/data/careers.ts 의 JobPosting 과 1:1)
create table job_postings (
  id            text primary key,           -- URL 슬러그. 예: 'ae-planner'
  title         text not null,
  job_group     text not null,              -- 기획|퍼포먼스|콘텐츠|바이럴|경영지원

  career_years  text,
  message       text,
  resume_path   text,                       -- Storage 경로
  portfolio_url text,
  status        text not null default 'received', -- received|screening|interview|offer|rejected
  memo          text,                       -- 인사팀 내부 메모
  privacy_agreed_at timestamptz not null,
  retention_until   date not null,          -- 보관기간 만료일 (F7)
  created_at    timestamptz not null default now()

-- 4.3 프로젝트 문의
create table inquiries (
  id          uuid primary key default gen_random_uuid(),
  company     text not null,
  name        text not null,
  phone       text not null,

create table admin_users (

create table audit_logs (

-- 4.8 연혁 (F14) — 현재 src/data/company.ts 의 history 구조와 1:1
create table history_entries (

create table org_divisions (

  sort_order int not null default 0

  id uuid primary key default gen_random_uuid(),

-- 4.10 클라이언트 목록 (F14) — 메인 롤링 밴드용
create table clients (
  id uuid primary key default gen_random_uuid(),
  name text not null unique,
  logo_path text,                        -- 로고 확보 시. null 이면 텍스트 노출

-- 4.11 팝업 배너 (C1) — 기간으로 자동 게시/종료
create table popups (
  id uuid primary key default gen_random_uuid(),
  title text not null, image_path text, link_url text,
  starts_at timestamptz not null, ends_at timestamptz not null,
  active boolean not null default true,
  created_at timestamptz not null default now()
);

-- 4.12 사이트 설정 (F16) — 기능 토글·소소한 설정의 key-value 저장
create table site_settings (
  key text primary key,                  -- 'feature.popup' | 'feature.stats' | ...
  value jsonb not null,
  updated_at timestamptz not null default now(),
  updated_by uuid
);

-- 4.13 어드민 알림 (F6) — 접수 이벤트를 어드민 화면에서 확인
-- 5인 소수 운영이라 알림은 전역 1행, 읽음 상태만 사용자별로 나눠 기록한다
create table notifications (
  id uuid primary key default gen_random_uuid(),
  type text not null,                    -- inquiry|application
  title text not null,                   -- '㈜○○ 프로젝트 문의'
  link text not null,                    -- '/admin/inquiries/<id>'
  created_at timestamptz not null default now()
);
create table notification_reads (
  notification_id uuid references notifications(id) on delete cascade,
  user_id uuid references admin_users(id) on delete cascade,
  read_at timestamptz not null default now(),
  primary key (notification_id, user_id)
);
```

**RLS(Row Level Security) 정책 요약**

- `job_postings` / `works`: `status='published'` 행만 익명 SELECT 허용. 쓰기는 어드민만
- `job_applications` / `inquiries`: 익명 INSERT만 허용, SELECT 전면 차단 (어드민은 서버 키로 조회)
- 개인정보 테이블은 **절대 클라이언트에서 직접 조회하지 않습니다**

## 5. API 설계

### 공개 API (비인증)

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/jobs` | 게시 중인 공고 목록 (`?group=퍼포먼스`) |
| GET | `/api/jobs/:id` | 공고 상세 (조회수 +1) |
| POST | `/api/jobs/:id/apply` | 지원 접수. 봇 토큰 검증 → INSERT → 알림 |
| POST | `/api/uploads/resume` | 이력서 업로드용 signed URL 발급 (확장자·용량 검증) |
| POST | `/api/inquiries` | 프로젝트 문의 접수 |
| GET | `/api/works` | 포트폴리오 목록 (F5 적용 후) |
| GET | `/api/brochure` | 최신 회사소개서 signed URL 발급 + 다운로드 카운트 (F13) |
| GET | `/api/site` | 연혁·조직도·클라이언트·활성 팝업·기능 토글을 한 번에 (F14·C1·F16) |

|---|---|---|

| GET/POST/PATCH/DELETE | `/api/admin/history[/:id]` | owner, editor |
| GET/POST/PATCH/DELETE | `/api/admin/org[/:id]` | owner, editor |
| GET/POST/PATCH/DELETE | `/api/admin/clients[/:id]` | owner, editor |
| GET/POST/PATCH/DELETE | `/api/admin/popups[/:id]` | owner, editor |
| POST | `/api/admin/brochure` | owner (PDF 업로드 → 최신본 교체) |

**공통 규칙**

- 접수 API는 IP당 분당 5회 레이트 리밋
- 요청 검증은 zod 스키마로 서버에서 재검증 (클라이언트 검증만 믿지 않음)
- 응답은 `{ ok: true, data }` / `{ ok: false, error: { code, message } }` 형태로 통일

## 6. 어드민 설계

### 6.0 디자인 방향 (2026-08-05 확정)

본 사이트 톤을 그대로 쓰되, 구조는 전문 SaaS 표준을 따른다.

- **토큰 재사용**: 노블 블루 `#2e80e8` 포인트, Pretendard, 본 사이트의 라이트/다크 테마 변수 공유
- **레이아웃**: 좌측 고정 사이드바(축소 가능) + 상단 브레드크럼·검색 + 콘텐츠 영역
- **목록**: 테이블 중심(상태 배지·필터 칩·검색·페이지네이션), 행 클릭 시 우측 슬라이드 패널 상세
- **등록 화면**: `임시저장 → 미리보기(실제 페이지 컴포넌트 렌더) → 게시` 3단계, 하단 고정 액션 바
- **배지·칩·버튼**: 본 사이트의 채용중/마감 배지, 필터 칩과 동일한 스타일 언어
- **알림센터**: 상단 바에 벨 아이콘 + 미읽음 배지. 클릭 시 드롭다운(최근 접수 목록 → 해당 상세로 이동).

### 6.3 공고 작성 화면

- **기본 정보**: 제목, 직군(셀렉트), 소속 팀, 고용형태, 경력, 근무지

- **한 줄 소개**: 목록 카드에 노출됨을 안내 (80자 권장, 카운터 표시)
- **주요 업무 / 자격 요건 / 우대 사항**: 항목 추가·삭제·순서 변경이 되는 리스트 입력

## 7. 개인정보·보안 요건

법적 의무이므로 구현 시 생략 불가한 항목입니다.

1. **수집 동의**: 폼 제출 시 필수 체크 + 동의 시각(`privacy_agreed_at`) 저장
2. **보관기간 고지·자동 파기**
   - 문의: 3년 / 지원서: 1년 (사내 규정 확정 필요)
   - 매일 배치(cron)로 `retention_until` 경과 건 삭제 + Storage 파일 동시 삭제
3. **개인정보처리방침 페이지 신설** — 현재 푸터 링크가 `#` ([Footer.tsx:50](../src/components/Footer.tsx#L50))
4. **암호화**: DB 저장 시 암호화(Supabase 기본 제공), 전 구간 HTTPS
5. **접근 통제**: 어드민 2FA, 세션 만료, 개인정보 열람·내보내기 전건 감사 로그
6. **업로드 검증**: 확장자 화이트리스트(pdf/doc/docx/hwp), 10MB 제한, MIME 재검사, 실행파일 차단
7. **봇 방지**: Cloudflare Turnstile(무료) + 허니팟 필드 + 레이트 리밋
8. **CSV 내보내기**: owner 전용, 다운로드 사유 입력, 로그 기록

### 11.1 GitHub 저장소 이전 (P1 후속 — 2026-08-05 Transfer 로 확정)

저장소를 `po-billy` → 회사 GitHub 계정 **`noblecompany`**(admin@e-noble.kr)로 **Transfer** 한다.
Vercel 로그인 계정과 저장소 소유자가 일치하게 되어 별도 권한 연결이 불필요해진다.

절차:
1. `po-billy` 로 저장소 → Settings → General 맨 아래 Danger Zone → **Transfer ownership**
   → 새 소유자 계정명 입력
2. 회사 계정에서 이전 수락
3. 이전 후 처리:
   - 로컬 remote 갱신: `git remote set-url origin https://github.com/<회사계정>/noble-preview.git`
   - **GitHub Pages 재게시** — Pages 는 이전 시 내려간다. 새 저장소 Settings → Pages →
     Source: GitHub Actions 재설정 후 워크플로 재실행. 프리뷰 URL 도
     `<회사계정>.github.io/noble-preview/` 로 바뀜
   - **PAT 재발급** — 기존 토큰은 po-billy 소유 저장소 한정이라 이전 후 푸시 불가.
     회사 계정에서 Fine-grained 토큰(Contents: Read and write, 해당 저장소만) 신규 발급

### 11.2 DNS 현황과 커트오버 계획 (2026-08-05 실사)

**핵심 발견: 현재 권한 네임서버는 가비아가 아니라 `ns0/ns1.webmaker21.kr`(현 홈페이지 제작사)다.**
가비아 DNS 관리 화면의 레코드 8개는 준비된 존이며, 네임서버를 바꾸기 전까지는 적용되지 않는다.

라이브 존(webmaker21) vs 가비아 준비 존 대조 결과:

| 레코드 | 라이브 (webmaker21) | 가비아 준비 존 | 조치 |
|---|---|---|---|
| A `@` | 115.68.17.176 (구 홈페이지 서버) | 없음 | **Vercel A `76.76.21.21` 추가** |
| `www` | `@` 별칭 | 없음 | **CNAME `cname.vercel-dns.com.` 추가** |
| MX | mailapp.hiworks.co.kr ✓ | ✓ 동일 | 그대로 |
| CNAME mail·pop3·webmail·hiworks·webmailhard | ✓ | ✓ 동일 | 그대로 |
| SPF | `v=spf1 include:_spf.hiworks.co.kr ~all` (최신형) | IP 나열 구버전 | **라이브의 include 형으로 교체** |
| TXT naver | 없음 | 있음 | 무해, 유지 |
| DKIM·DMARC | 없음 | 없음 | 현행 유지 (추후 HIWORKS에서 DKIM 발급 권장) |

**커트오버 순서 (메일 무중단이 최우선)**

1. 새 사이트가 Vercel에서 임시 도메인으로 완전히 동작하는 것을 확인한 뒤 진행
2. 가비아 DNS 관리에서: SPF를 `include:_spf.hiworks.co.kr` 형으로 교체,
   A `@` → `76.76.21.21`, CNAME `www` → `cname.vercel-dns.com.` 추가 (메일 레코드는 손대지 않음)
3. Vercel 프로젝트에 `e-noble.kr`·`www.e-noble.kr` 도메인 등록
4. 가비아에서 네임서버를 webmaker21 → **가비아 네임서버**로 변경
5. 전파 대기(최대 24~48h) 후 확인: 웹 접속, HIWORKS 메일 수발신 테스트, `nslookup` 재검증
6. 이상 없으면 webmaker21 호스팅 계약은 정리 대상 (구 사이트 백업 먼저)

**기타 자산**: 가비아 이미지호스팅 `enoble.speedgabia.com` (베이직, 2028-06-30 만기, 2.6/10GB 사용)
— 구 사이트 이미지용으로 추정. 새 사이트는 사용하지 않으므로 커트오버 후 만기 시 정리 검토.
